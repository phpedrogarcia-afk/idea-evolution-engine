## 1. Executive Summary

During the execution of `FREE-SACRIFICIAL-PILOT-005` on the Groq Free tier (`openai/gpt-oss-120b`), the primary request for `CONDITION_C` (Call 1, `LEAN_FIRST_PASS`) failed with `HTTP 400 Bad Request` (`json_validate_failed`).

Thanks to the observability patch committed in `65b5e0e2a84611f3fc17dc10b56b0889765d1a88`, detailed sanitized provider error metadata was captured in the append-only ledger (`usage-ledger.jsonl`).

### Core Findings
1. **Identical Semantic Payload:** The exact same prompt, model, system instruction, JSON schema, temperature (0.3), and token cap (2048) was dispatched in Pilots 001, 002, 003, 004, and 005 (sanitized payload SHA: `2cb4117f7b75ea4e150f508e32223c7f8a283e19144d1caf1d4fb9e05ea2bde6`).
2. **Intermittent Outcome:** Pilots 001, 003, and 004 succeeded with `HTTP 200` (consuming 1909, 2008, and 1593 completion tokens respectively). Pilots 002 and 005 failed with `HTTP 400`.
3. **Failure Mechanism:** Groq's error message explicitly reports:
   > `Generated JSON does not match the expected schema. Please adjust your prompt. See 'failed_generation' for more details. Error: jsonschema: '' does not validate with /required: missing properties: 'remaining_uncertainties', 'requires_human_normative_choice', 'human_choice_description', 'proposed_next_action'`
   The schema itself was accepted by Groq at request time; the backend model (`openai/gpt-oss-120b`) failed post-generation schema validation because the generation stopped before producing the final 4 required properties.
4. **Classification:** `PROVIDER_INTERMITTENT_SCHEMA_REJECTION`.

## 6. Local Schema vs. Provider Rejection Verification

### Local Schema Investigation
1. **Did local JSON Schema change?** **NO.** `to_strict_json_schema(LeanFirstPassOutput)` produces `200fafea9a63d958b40c752fd3a4998721ebd47b948cd8cbf156cf272014c529`, identical to the schema used since M05.4.
2. **Did strictness change?** **NO.** `strict: True` in all attempts.
3. **Did required / additionalProperties change?** **NO.** All 11 properties are required; `additionalProperties: False`.
4. **Did message construction change?** **NO.** `system_instruction` and `user_prompt` are identical.
5. **Did output cap change?** **NO.** Fixed at 2048 tokens.

### Rejection Mechanism
The Groq error `json_validate_failed` with message:
`missing properties: 'remaining_uncertainties', 'requires_human_normative_choice', 'human_choice_description', 'proposed_next_action'`
indicates that the model generated properties 1 through 7 of `LeanFirstPassOutput` (`interpreted_problem`, `human_intent`, `primary_mechanism`, `competing_alternatives`, `key_assumptions`, `material_ambiguities`, `material_vulnerabilities`), but ran out of generation capacity (or prematurely stopped) before emitting properties 8 through 11.

In Pilot 003, generating all 11 properties required **2008 tokens**, which is within 40 tokens of the 2048 cap. Under `temperature = 0.3`, minor variations in generation length occasionally cause the output to be truncated at 2048 tokens. Groq then validates the incomplete JSON against the required fields and rejects it with HTTP 400.

## 7. Root Cause Classification

**Classification:** `PROVIDER_INTERMITTENT_SCHEMA_REJECTION`  
**Confidence:** `HIGH`

### Justification:
- The exact same request payload (`sanitized_payload_sha256: 2cb4117f7b75...`) was dispatched 5 times.
- It succeeded 3 times (Pilots 001, 003, 004) with HTTP 200.
- It failed 2 times (Pilots 002, 005) with HTTP 400 `json_validate_failed`.
- No local deterministic difference exists between the successful and failed executions.
- The failure is caused by stochastic token consumption near the 2048 token boundary, resulting in incomplete generation and post-generation rejection by Groq's validator.
