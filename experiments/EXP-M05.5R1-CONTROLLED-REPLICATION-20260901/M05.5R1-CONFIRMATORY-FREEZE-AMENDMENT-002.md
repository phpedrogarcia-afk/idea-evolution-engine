## 1. Rationale for Amendment

A execução da tentativa confirmatória `REAL-EXECUTION-ATTEMPT-003` (commit `8fb51c7`) foi interrompida na Célula 2 (`H08-CONDITION_B`, etapa `UNDERSTAND`) devido a uma rejeição de schema estrito do lado do servidor Groq:
```
HTTP 400 Bad Request
provider_error_code = json_validate_failed
failed_generation = PRESENT
missing properties: 'proposed_mechanism'
```

Esta anomalia concreta é idêntica à observada na autópsia forense do `FREE-SACRIFICIAL-PILOT-005` (`b0c7fc9`). O mesmo prompt e schema geraram **HTTP 200 OK** na tentativa `REAL-EXECUTION-ATTEMPT-002` e no piloto `FREE-SACRIFICIAL-PILOT-006`. Trata-se comprovadamente de uma falha intermitente de entrega do provedor sob amostragem estocástica (temperatura 0,3), e **não** de um bug de schema local.

Sob a política anterior de zero retries de transporte (`MAX_TRANSPORT_RETRIES_PER_REQUEST = 0`), um único erro estocástico de validação de schema do provedor aborta irreversivelmente a tentativa inteira.

Esta emenda introduz prospectivamente uma regra estreita e delimitada de resiliência de entrega de schema estrito, aprovada formalmente pelo supervisor (`SUPERVISOR_DECISION = APPROVE_ONE_NARROW_PROVIDER_RESILIENCE_RULE`).

## 2. Regra Estrita de Resiliência de Schema Delimitada

1. **Parâmetro Limite:**
   `MAX_IDENTICAL_STRICT_SCHEMA_REPLAYS_PER_LOGICAL_CALL = 1`
2. **Critério Exato de Elegibilidade:**
   Um replay idêntico de schema estrito é permitido **EXCLUSIVAMENTE** quando:
   - `HTTP_STATUS == 400`
   - `PROVIDER_ERROR_CODE == "json_validate_failed"`
   - `FAILED_GENERATION_PRESENT == True`
   - A requisição já havia sido despachada sob o contrato de output estruturado estrito congelado.
   - Nenhuma outra classe de erro qualifica (401, 403, 404, 422, 429, 5xx, timeout de rede, truncamento, BAD_REQUEST genérico permanecem sob suas regras congeladas existentes).
3. **Identidade Estrita do Payload:**
   Antes do replay, é verificado matematicamente que `ORIGINAL_SANITIZED_PAYLOAD_SHA256 == REPLAY_SANITIZED_PAYLOAD_SHA256`.
   Nenhum campo, prompt, schema, temperatura ou token cap é alterado ou reparado.
4. **Contabilidade Científica:**
   - A chamada lógica semântica do tratamento permanece **UMA ÚNICA** chamada (`LOGICAL_SEMANTIC_CALLS = 1`).
   - O número de requisições ao provedor é registrado como `2` (`PROVIDER_REQUESTS = 2`).
   - O replay não consome slot adicional do teto de chamadas do tratamento B ou C.
5. **Proibição de Amostragem por Qualidade:**
   O replay existe unicamente para recuperar a entrega de máquina ilegível pelo provedor. Assim que uma resposta válida sob o schema for obtida, ela é aceita imediatamente. Não há re-amostragem por conteúdo.
6. **Segunda Falha Idêntica é Terminal:**
   Se a tentativa de replay também retornar `HTTP 400 json_validate_failed`, a execução é abortada imediatamente. Não há terceira tentativa.
7. **Pacing Preservado:**
   A verificação de capacidade TPM/TPD (`wait_for_tpm_capacity`) e pre-dispatch são executadas antes do replay.
